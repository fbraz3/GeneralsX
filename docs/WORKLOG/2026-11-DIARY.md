### Pin Windows CI vcpkg toolchain and bump binary cache to v4
- **Problem**: Windows CI builds (`Build Windows / generalsxzh x86` and `Build Windows / generalsx x86`) were taking over 42-44 minutes, frequently hitting or bordering the 45-minute workflow timeout and causing CI failures.
- **Root cause (`build-windows.yml`)**:
  - `build-windows.yml` did not pin the `vcpkg` binary or toolchain; instead, it relied on `$env:VCPKG_INSTALLATION_ROOT` pointing to the runner image's preinstalled vcpkg (`C:\vcpkg`).
  - GitHub Actions updates the `windows-2022` runner image weekly. Each runner image update rolls out a newer `vcpkg` executable commit, which changes the computed package ABI hashes for dependencies (`protobuf:x64`, `protobuf:x86`, `curl`, `openssl`, `abseil`, `gamenetworkingsockets`).
  - The cache key (`vcpkg-bincache-v3-${{ runner.os }}-x86-msvc-v143-${{ hashFiles('vcpkg.json', 'vcpkg-lock.json', 'cmake/ports/**', 'cmake/triplets/**') }}`) only tracked manifest and overlay files, omitting the vcpkg toolchain/commit and workflow file. As a result, GitHub Actions restored stale cache archives with mismatched package ABIs, reporting `Restored 0 package(s)`.
  - Because `actions/cache/restore` found an exact primary key hit from a previous runner image, `steps.vcpkg_cache.outputs.cache-hit` evaluated to `true`. This caused `actions/cache/save` to skip saving the freshly compiled packages (which took ~37 minutes), trapping all subsequent runs on every branch in a permanent 42-minute recompilation loop.
- **Fix**:
  - Integrated `lukka/run-vcpkg@v11` into `build-windows.yml` pinned to commit `ffc071e0c08432c60c9b64f00334c0227667931b`, matching `build-macos.yml` and `build-linux.yml` for reproducible cross-platform toolchains.
  - Preserved the pinned `VCPKG_ROOT` in the CMake configure step (`if (-not $env:VCPKG_ROOT) { $env:VCPKG_ROOT = $env:VCPKG_INSTALLATION_ROOT }`).
  - Bumped the binary cache key prefix to `vcpkg-bincache-v4-` and included `.github/workflows/build-windows.yml` in `hashFiles(...)` so workflow and toolchain modifications automatically invalidate and rotate cache keys.
  - Purged obsolete `vcpkg-bincache-v3-` cache records from GitHub Actions cache storage.

### Fix speedup after in-game save load by re-evaluating logic time scale (#334)
- **Problem**: Loading a savegame from inside a running match caused the simulation to run at 60 FPS (double speed) instead of the intended 30 ticks/sec simulation rate.
- **Root cause (`GameState.cpp`)**:

### Fix auto-defeat in General's Challenge on next match and retry (#328, #390)
- **Problem**: In Zero Hour's General's Challenge mode, completing a challenge match and pressing "Save & Continue" (or pressing "Retry" on defeat) triggered an immediate "You have been defeated" screen during the next match's intro cutscene. However, loading the auto-saved mission savegame worked normally without defeating the player.
- **Root cause (`Shell.cpp`, `ScoreScreen.cpp`, `QuitMenu.cpp`, `GameLogic.cpp`)**:
  - In `startNextCampaignGame()` (`ScoreScreen.cpp`), advancing to the next challenge mission or retrying a lost mission calls `TheShell->popImmediate()` to dismiss `ScoreScreen.wnd`.

### Fix W3DModelDraw recoil list crash in China mission 7 (#379)
- **Problem**: In China mission 7, the game crashed during weapon firing due to an out-of-bounds access / empty recoil vector.
- **Root cause (`W3DModelDraw.cpp`)**:
  - `specificBarrelToUse > wbvec.size()` allowed indexing at `wbvec.size()`, which is an off-by-one out-of-bounds error.
  - The recoil list `m_weaponRecoilInfoVec[wslot]` is sized when the model state is set. - **Fix**:
  - Fixed off-by-one boundary check: `specificBarrelToUse >= (Int)wbvec.size()`.

  - Patch originally reported and provided by [@Moortu](https://github.com/Moortu).

### Fix OpenAL audio stream hissing voice sound (#380)
- **Problem**: In campaign maps, voice lines could leave behind a continuous hissing or looping sound artifact.
- **Root cause (`OpenALAudioStream.cpp`)**: When an OpenAL source transitions to `AL_STOPPED`, it has completed playback of all queued buffers, and OpenAL flags them as processed. Calling `play()` on a stopped source rewinds it and replays the old buffers again. Consequently, the final chunk of speech lines looped indefinitely and the stream was never released.
- **Fix**:
  - In `OpenALAudioStream::update()`, explicitly detect `sourceState == AL_STOPPED && num_queued > 0`, unqueue and drop stale played buffers while preserving any freshly queued buffers added immediately prior to `update()`.
  - Restricted the subsequent restart check to `AL_INITIAL` and `AL_PAUSED`.
  - Patch provided by [@Moortu](https://github.com/Moortu) with subsequent frame preservation hardening.
