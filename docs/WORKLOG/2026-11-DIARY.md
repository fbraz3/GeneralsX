### Fix auto-defeat in General's Challenge on next match and retry (#328, #390)
- **Problem**: In Zero Hour's General's Challenge mode, completing a challenge match and pressing "Save & Continue" (or pressing "Retry" on defeat) triggered an immediate "You have been defeated" screen during the next match's intro cutscene. However, loading the auto-saved mission savegame worked normally without defeating the player.
- **Root cause (`Shell.cpp`, `ScoreScreen.cpp`, `QuitMenu.cpp`, `GameLogic.cpp`)**:
  - In `startNextCampaignGame()` (`ScoreScreen.cpp`), advancing to the next challenge mission or retrying a lost mission calls `TheShell->popImmediate()` to dismiss `ScoreScreen.wnd`.
  - In `Shell::popImmediate()`, `doPop(FALSE)` was called without suppressing uncovered layout initialization (`newTop->runInit(nullptr)`). Because `ChallengeMenu.wnd` is dormant on the shell stack beneath `ScoreScreen.wnd`, `ChallengeMenuInit` was invoked.
  - `ChallengeMenuInit` calls `TheChallengeGameInfo->clearSlotList()` and `reset()`, wiping slot 0 (the local human player slot) and setting its state to `SLOT_CLOSED`. Additionally, `ChallengeMenuInit` invoked `TheShell->showShellMap(TRUE)`, queueing a conflicting `MSG_NEW_GAME(GAME_SHELL)` and overwriting `m_pendingFile`.
  - When `MSG_NEW_GAME(GAME_SINGLE_PLAYER)` executed in `GameLogic::startNewGame`, `TheGameInfo` (`TheChallengeGameInfo`) had all slots cleared. Consequently, `placeNetworkBuildingsForPlayer()` was skipped, leaving the player with 0 structures and 0 units. Map scripts detecting 0 player buildings fired `ScriptActions::doDefeat()` seconds into the mission.
  - Loading the mission savegame bypassed `startNextCampaignGame()`; `GameState::loadGame` restored `TheChallengeGameInfo` with slot 0 intact from the save snapshot, which is why loading always worked.
- **Fix**:
  - **`Shell.h` & `Shell.cpp`**: Added `runNewTopInit` flag (default `TRUE`) to `popImmediate()` and `doPop()`. When popping layouts to transition directly into a game, `runNewTopInit = FALSE` suppresses `runInit()` on dormant menus beneath the stack, preventing accidental menu resets and shell map activations. Also guarded `doPop` initialization with `m_isShellActive`.
  - **`ScoreScreen.cpp` (ZH & Generals base game)**: Updated `startNextCampaignGame()` to call `TheShell->popImmediate(FALSE)` before `TheShell->hideShell()`, ensuring dormant menus are not re-initialized. Configured `TheChallengeGameInfo` with the player's general and slot 0, and passed the rendering FPS limit to `MSG_NEW_GAME`.
  - **`QuitMenu.cpp` (ZH)**: In `restartMissionMenu()`, ensured `TheChallengeGameInfo` is re-initialized for the challenge map when restarting mid-game from the pause menu.
  - **`GameLogic.cpp` (ZH)**: Allowed `isChallengeCampaign` in `DEBUG_ASSERTCRASH(m_gameMode == GAME_SKIRMISH || isChallengeCampaign)` so restarts do not fail debug assertions when preserving setup.
- **Validation**:
  - Clean compilation of `GeneralsXZH` target on macOS (`build/macos-vulkan`).
  - Clean compilation of base game `GeneralsX` target on macOS (`build/macos-vulkan`).

### Fix W3DModelDraw recoil list crash in China mission 7 (#379)
- **Problem**: In China mission 7, the game crashed during weapon firing due to an out-of-bounds access / empty recoil vector.
- **Root cause (`W3DModelDraw.cpp`)**:
  - `specificBarrelToUse > wbvec.size()` allowed indexing at `wbvec.size()`, which is an off-by-one out-of-bounds error.
  - The recoil list `m_weaponRecoilInfoVec[wslot]` is sized when the model state is set. If that occurs before the shared weapon barrel info of the state is validated (only built during a logic update), the recoil list remains empty when weapon fire effects or client recoil updates trigger, causing an out-of-bounds access or assertion failure.
- **Fix**:
  - Fixed off-by-one boundary check: `specificBarrelToUse >= (Int)wbvec.size()`.
  - Synchronized recoil lists across all weapon slots to their validated barrel count in both `handleWeaponFireFX()` and `handleClientRecoil()`, preserving existing recoil states while preventing out-of-bounds access and assertion failures.
  - Patch originally reported and provided by [@Moortu](https://github.com/Moortu).
