## 2026-10-01: Fix Replay Test Crash 0xC000007B (Non-x64 DLL Pollution) and Optimize Configure/Build Caches

### Context & Root Cause
1. **Windows SDL3 Replay Tests Loader Crash (`0xC000007B`)**:
   - Following the self-contained Windows bundle packaging changes in commit `a3eec808a`, the Windows SDL3 x64 build succeeded on both `generalsx` and `generalsxzh`, but `Replay Tests (windows SDL3 x64)` failed with exit code `-1073741701` (`0xFFFFFFFFC000007B`, `STATUS_INVALID_IMAGE_FORMAT`) before producing output.
   - Inspection of the packaged artifact (`windows-bundle-generalsxzh-windows64-deploy`) identified two 32-bit (x86 / `IMAGE_FILE_MACHINE_I386` = 0x14C) binaries inside the bundle:
     - `image.dll` (6,656 bytes, OpenSSL engine module)
     - `libavif-16.dll` (9,308,160 bytes, 32-bit image codec DLL)
   - Because `deploy-windows-zh.ps1` and `deploy-windows-generals.ps1` recursively copied DLLs from `vcpkg_installed` without verifying the destination `bin/` path or PE architecture, and searched `$buildDir` during transitive dependency resolution without PE architecture validation, incompatible 32-bit DLLs entered the 64-bit application bundle.
   - When `GeneralsXZH.exe` launched, the Windows loader attempted to load these x86 images into an AMD64 64-bit process space, resulting in instant crash `0xC000007B`.

2. **Pipeline Duration and Configure Cache Opportunities**:
   - The Windows SDL3 build jobs were taking ~30-40 minutes total, with configure taking ~3 minutes and ninja compilation taking ~24 minutes.
   - During CMake configure, FetchContent repeatedly cloned/downloaded repositories (`min-dx8-sdk`, `dxvk`, `sdl3`, `gamespy`, `openal`, `sagepatch`, `nextgenmp`) on every run because `build/windows64-deploy/_deps` was not cached in CI.
   - `configure-windows64.ps1` was executing an explicit `vcpkg install` command even during the CMake configure step, despite CMake's `vcpkg.cmake` toolchain automatically handling manifest package resolution (`VCPKG_MANIFEST_MODE: ON`).
   - `ccache` in the Windows SDL3 job was only storing ~27 MB (compared to ~156 MB on macOS) due to missing `CCACHE_BASEDIR=${{ github.workspace }}` and `CCACHE_SLOPPINESS=time_macros,include_file_mtime,locale` settings, causing compiler cache misses across runner instances due to varying absolute file paths.

### Changes Applied
1. **Strict 64-bit PE Architecture Enforcement (`deploy-windows-zh.ps1`, `deploy-windows-generals.ps1`)**:
   - Added `Test-IsPe64` helper checking the DOS `MZ` header, PE signature `0x00004550`, and PE Machine type `IMAGE_FILE_MACHINE_AMD64` (`0x8664`).
   - Restricted vcpkg DLL copying to release runtime binaries (`*/bin/*`) that strictly pass `Test-IsPe64`.
   - Guarded MinGW and transitive dependency resolution with `Test-IsPe64`, discarding any non-x64 candidate.
   - Added a final sweep pass across `$bundleDir` to remove any non-x64 DLL before packaging.
2. **CI Bundle Verification (`build-windows-sdl3.yml`)**:
   - Added an automated PE inspection loop in `Verify Bundle Output and Packaged DLLs` that verifies every `.dll` in the bundle is strictly 64-bit AMD64 (`0x8664`).
3. **Configure & Build Cache Optimizations (`build-windows-sdl3.yml`, `configure-windows64.ps1`, `cmake/ccache.cmake`, build scripts)**:
   - Added CMake FetchContent cache step (`build/windows64-deploy/_deps`) keyed by CMake files hash (`fetchcontent-windows64-${{ hashFiles('cmake/**', 'CMakeLists.txt') }}`).
   - Guarded manual `vcpkg install` invocation in `configure-windows64.ps1` behind `-InstallDependenciesOnly`, eliminating duplicate vcpkg calls during CMake configure.
   - Configured `CCACHE_BASEDIR=${{ github.workspace }}`, `CCACHE_SLOPPINESS=time_macros,include_file_mtime,locale`, `CCACHE_COMPILERCHECK=content`, and `CCACHE_MAXSIZE=2G` in `build-windows-sdl3.yml`.
   - Updated `cmake/ccache.cmake` to set `ENV{CCACHE_SLOPPINESS}` on Windows/MinGW as well as macOS.
   - Added `ccache -s` statistics logging before and after compilation in `build-windows-zh.ps1` and `build-windows-generals.ps1`.
