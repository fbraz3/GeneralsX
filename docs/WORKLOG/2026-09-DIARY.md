### 05/09/2026 - Fix WebSocket SNI TLS Handshake & Automatic Connection Recovery
- **Context**: During cross-play multiplayer testing between macOS and Windows in production, the Mac client did not show the `[MAC]` platform tag, did not display other players in the lobby, did not display created games, and showed an empty slot roster upon creating a staging room.
- **Root Cause Analysis**:
  1. **TLS SNI Disabled by `CURLOPT_SSL_VERIFYHOST = 0`**: In `OnlineServices_WebSocket.cpp`, `curl_easy_setopt(m_curl, CURLOPT_SSL_VERIFYHOST, 0L)` was set. Under Apple's SecureTransport (used by libcurl on macOS), disabling hostname validation explicitly disables Server Name Indication (SNI). Because the production GameServer (`generalsonline.braz.cloud`) is fronted by Cloudflare's TLS edge, Cloudflare rejected the TLS handshake without SNI (`Result: 35 (SSL connect error)`).
  2. **Silent Failure & Missing WebSocket Updates**: Because WebSocket connection failed immediately on login, the client never connected to `/ws`. The REST API calls (`POST /CheckLogin`, `GET /PlayerStats`, `GET /GlobalStats`, `PUT /Lobbies`) succeeded over HTTPS, but all real-time push events—such as room rosters (`NETWORK_ROOM_MEMBER_LIST_UPDATE`), platform tags (`[MAC]`, `[WIN]`), lobby updates (`NETWORK_ROOM_LOBBY_LIST_UPDATE`), and staging room slot updates (`LOBBY_CURRENT_LOBBY_UPDATE`)—are delivered exclusively over WebSocket.
  3. **No Reconnection or Error Visibility**: `changeNetworkRoom(0)` and `sendRawWebSocketPayload()` silently ignored dead sessions without attempting reconnect, and `run.sh` did not persist stdout/stderr to disk.
- **Solutions Implemented**:
  1. **Enable SNI in WebSocket (`OnlineServices_WebSocket.cpp`)**: Set `CURLOPT_SSL_VERIFYHOST, 2L` and `CURLOPT_SSL_VERIFYPEER, (NGMP::IsDevelopment() ? 0L : 1L)`, restoring SNI and allowing seamless TLS handshake with Cloudflare edge.
  2. **Automatic Connection Recovery (`OnlineServices_Manager.h/cpp`)**: Implemented `ensureWebSocketConnected()`, invoked on `EVENT_AUTH_SUCCESS`, before sending payloads in `sendRawWebSocketPayload()`, on room changes in `changeNetworkRoom()`, and in `WOLGameSetupMenuInit()`.

### 06/09/2026 - Fix Windows MSVC uint32 Redefinition in Zero Hour Build
- **Context**: Windows Zero Hour CI build failed in [Run #34013105259](https://github.com/fbraz3/GeneralsX/actions/runs/34013105259) with `steamtypes.h(51): error C2371: 'uint32': redefinition; different basic types` while compiling `OnlineServices_Manager.cpp`.

### 07/09/2026 - Eliminate GNS STUN KeepAlive Thinker Starvation on Virtual/Tunnel Interfaces
- **Context**: Testing multiplayer between Windows (`kurteago`) and macOS (`fbraz3`). Even with TURN disabled, the match timed out attempting to connect and dropped to `ScoreScreen.wnd`.
- **Root Cause Analysis (Local & Server Logs)**:
  - Windows logs (`logs/generalsx_utf8.log`) confirmed Windows dispatched multiple `NETWORK_SIGNAL (12)` candidate bursts containing its `192.168.1.5` host candidates and public reflexive candidates.
  - Server logs (`generalsonline_server`) confirmed receipt of `NETWORK_SIGNAL (12)` and `NETWORK_CONNECTION_CLIENT_REQUEST_SIGNALLING (19)` from Windows, but 0 signals from macOS (`fbraz3`).
  - macOS logs (`logs/run_zh_macos.log`) revealed identical 10,001 thinker loop warnings:
    ```text
    [STEAM SOCKETS][1] Processed thinkers 10001 times -- probably one thinker keeps requesting an immediate wakeup call.
    [STEAM SOCKETS][4] SteamNetworkingSockets lock held for 112.2ms. (Performance warning.) ServiceThread,CSteamNetworkingSocketsSTUNRequest::Think(x10000),SendUDPacket(x10000)
    ```
  - Deep inspection of Valve's GameNetworkingSockets (`steamnetworkingsockets_ice_client.cpp:2298-2304`):
    - macOS has virtual tunnel interfaces (Tailscale `utun3` IPv4/IPv6).
    - When `GatherInterfaces` opens raw UDP sockets, sending to STUN servers over unroutable tunnel interfaces fails immediately at socket level.
    - `SendPacketGather` fails and fires `STUNRequestCallback_ServerReflexiveKeepAlive` without delay.
    - The callback executes:
      ```cpp
      const int nSTUNServerIdx = std::max( 0, index_of( m_vecSTUNServers, info.m_pRequest->m_remoteAddr ) );
      const int nNextSTUNServerIdx = ( nSTUNServerIdx + 1 ) % len( m_vecSTUNServers );
      pIntf->QueueBindRequest( m_vecSTUNServers[ nNextSTUNServerIdx ], ... );
      ```
    - Modulo cycling `(n + 1) % len` queues the next STUN server with `SetNextThinkTimeASAP()`, creating an infinite zero-delay loop bounded only by the 10,001 thinker safety threshold.
    - This holds the GNS mutex continuously for >100ms per frame, completely starving `ThinkConnection` from sending ICE candidates or connection responses.
- **Solution (`NetworkMesh.cpp`)**:
  - Disabled `P2P_STUN_ServerList` by setting it to `""` in both `NetworkMesh::NetworkMesh()` and `NetworkMesh::SetTURNCredentials()`.
  - When `m_vecSTUNServers` is empty, GNS skips reflexive candidate discovery and keepalive thinkers entirely (`m_vecSTUNServers.empty() -> return`).
  - Local host candidates (`typ host`, e.g. `192.168.1.11` on macOS and `192.168.1.5` on Windows) are discovered and exchanged cleanly without any STUN socket traffic, allowing immediate LAN P2P connectivity without thread starvation.

  - macOS build initiated (`build-macos-zh.sh`).
