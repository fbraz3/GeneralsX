### Encode supplementary characters as surrogate pairs in save game unicode strings (`fix/issue-443-savegame-unicode-width`, PR #444 review)
- **Problem**: Two CodeRabbit findings on PR #444. Where `WideChar` is 4 bytes, `UnicodeString` holds whole code points and counts them with `wcslen`, so a character outside the basic multilingual plane is one character, not the surrogate pair the file format stores. The writer cast each character to `UnsignedShort`, which turned `U+1F600` into `U+F600` and produced a save that cannot round-trip the original text, and it took the length header from the character count rather than from the number of code units written. The reader copied each code unit into the native buffer, so a surrogate pair read back as two unpaired surrogates instead of the one character they stand for, which also left the retail saves that contain such a pair decoding wrong.
- **Fix**: `XferSave::xferUnicodeString` encodes the string into UTF-16 before writing anything: a code point above `U+FFFF` becomes a surrogate pair, one above `U+10FFFF` becomes `U+FFFD`, and the length header is the encoded code unit count. The 255 unit limit the single length byte imposes is now applied to that encoded length rather than to the character count, so 128 supplementary characters are refused where 127 of them plus one BMP character still fit. `XferLoad::xferUnicodeString` combines a high surrogate followed by a low one into a single character when `WideChar` is wider than 2 bytes, and leaves an unpaired surrogate as it is instead of swallowing the unit behind it. On Windows no code point can exceed `U+FFFF`, so both paths stay the identity copy they were and the written bytes are unchanged. Both functions live in `Core/`, so Generals and Zero Hour share the fix.
- **Verification**: The engine does not build on this host (no `cmake`, and the Google Test targets link `comctl32`/`imm32`/`vfw32`/`winmm`), so the test suite was not run locally. The two loops were extracted verbatim into a standalone harness and compiled with `g++ -std=c++17 -Wall -Wextra`, once with `wchar_t` (4 bytes) and once with `char16_t` (2 bytes) to stand in for Windows. Both widths pass the same 11 checks: BMP strings keep one unit per character and round-trip, `U+1F600` encodes to `D83D DE00` and round-trips alone and inside a sentence, a surrogate pair coming from a file the writer did not produce decodes to one character, an unpaired surrogate survives untouched, 128 supplementary characters are refused at 256 units, and 127 of them plus `A` encode to exactly 255 units and round-trip. Six Google Test cases covering the same ground were added to `Tests/Google/Core/GameEngine/Common/XferUnicodeStringTest.cpp`, including a reader fixture fed with hand-written bytes rather than writer output, and are left for CI to run.
- **Follow-up**: CodeRabbit and Greptile both flagged the new rejection test on the second review round. `XferSave::xferUnicodeString` reports the string it refuses with `DEBUG_CRASH` before it throws, and `GoogleTestMain.cpp` installs `failTestOnCrash`, which calls `ADD_FAILURE()`, so the test failed in debug builds although the writer behaved correctly. `EXPECT_THROW` catches the exception but does not clear that failure. The test now installs its own crash handler around the call that is expected to crash through the `DebugGetCrashHandler` / `DebugSetCrashHandler` pair that `Lib/Debug.h` exposes outside the `DEBUG_CRASHING` guard, restores the previous handler on scope exit, and asserts on the recorded message where `DEBUG_CRASHING` is enabled.

### Write and read save game unicode strings as 2 byte UTF-16 code units (`fix/issue-443-savegame-unicode-width`, #443)
- **Problem**: `XferSave::xferUnicodeString` and `XferLoad::xferUnicodeString` transfer `sizeof( WideChar ) * len` bytes, and `WideChar` resolves to `wchar_t` through `unichar`, which is 2 bytes on Windows but 4 bytes on Linux and macOS. The save file layout therefore depended on the writing platform, and a file written by the retail Windows game was read with characters twice as wide as they are: the Load Game list showed only every second character of the description (`Début de mission : USA 2` rendered as `Dbtd iso éignrlaoiu` plus replacement boxes), and the read ran 2x past the string, so the map label, campaign side and mission number that `xferSaveGameInfo` stores behind the description were all read from the wrong file position.
- **Fix**: `XferSave::xferUnicodeString` now converts the string into a `UnsignedShort` buffer and writes `sizeof( UnsignedShort ) * len` bytes; `XferLoad::xferUnicodeString` reads the same width into a `UnsignedShort` buffer and widens it into the native `WideChar` buffer. `MAX_XFER_UNICODE_STRING_LEN` was added to `Core/GameEngine/Include/Common/Xfer.h` for the 255 code unit limit the single length byte imposes. The on-disk layout is now the retail one on every platform, and on Windows the conversion is an identity copy that leaves the written bytes unchanged. Both functions live in `Core/`, so Generals and Zero Hour share the fix. `Xfer::xferUnicodeString` (used by `XferCRC`) and `XferDeepCRC::xferUnicodeString` carry the same `sizeof( WideChar )` pattern but feed CRCs rather than the save file, and were left out of scope because changing them shifts CRC values.
- **Verification**: `cmake --preset linux64-deploy` in the project Docker builder, then `z_generals` and `g_generals` both link clean with the change (`GeneralsMD/GeneralsXZH`, `Generals/GeneralsX`, 0 errors). The new test translation unit compiles for both the `z_googletest` and `g_googletest` objects. The `z_googletest` executable does not link on this preset because `z_wwaudio` fails to compile against the Miles stubs (`'HSTREAM' does not name a type`, `'::AIL_init_sample' has not been declared`); that failure reproduces on a clean checkout with the change stashed, so it is pre-existing and unrelated, and the Google Test cases could therefore not be executed here. Behaviour was instead verified with a standalone harness holding the old and the new function bodies verbatim, run against a retail written `00000000.sav` at the description length byte (offset `0x44`), with `sizeof(wchar_t) == 4`: the old read returns invalid code points, ends at file position 165 of a 192 byte file whose `CHUNK_GameState` payload is 118 bytes, and the `MD_USA01.map` map label behind it comes back as a short read; the new read returns `Début de mission : USA 2`, ends at position 117, and reads the map label correctly. The new writer reproduces the 49 retail bytes of that description exactly.

### Send /31 point-to-point tunnel discovery to the peer, not the local address (`fix/issue-429-wg-lan-interfaces`, PR #430 review)
- **Problem**: CodeRabbit finding on PR #430: on a pure point-to-point link with a `/31` netmask (RFC 3021 — no network or subnet-directed broadcast address), the all-ones derivation `(hostAddr & mask) | ~mask` in `getSubnetBroadcastAddresses()` returns the local address itself on the odd host of the pair (e.g. `10.8.0.3/31` yields `10.8.0.3`), so `LANAPI` queued discovery/announce packets to this host instead of the peer.
- **Fix**: In the P2P branch of `StdLANInterface::getSubnetBroadcastAddresses()`, a `/31` netmask no longer uses the all-ones derivation: the destination is the peer address from `ifa_dstaddr` when the interface reports one (PPP-style links); when none is reported (WireGuard tunnels report no peer) the interface contributes no discovery destination and `LANAPI` falls back to the global broadcast. `/31` links stay eligible for local-address enumeration via `IsUsableInterface()`/`HasSubnetNetmask()`, and the `/24`-style subnet-broadcast derivation is unchanged.
- **Verification**: `g++` compile of the translation unit with the `linux64-deploy` `compile_commands.json` flags, clean. ### Fix disappearing foliage and circular blob tree shadows (`fix_foliage_lod_shadows`)
- **Problem**:
  - After recent graphics improvements (#365 / #368), bushes frequently disappeared whenever moving the camera, and batched trees popped in/out while rendering old circular ground decal shadows underneath instead of projected tree shadows.
- **Root Causes**:
  1. **Water mirror pass hijacked tree & prop culling (`W3DTreeBuffer::drawTrees`, `W3DPropBuffer::drawProps`)**: `WaterRenderObjClass::renderMirror()` renders before the main camera pass with `ShaderClass::Invert_Backface_Culling(true)` using a reflected, screen-cropped, oblique-clipped camera. Because `drawTrees()` and `drawProps()` did not check `!ShaderClass::Is_Backface_Culling_Inverted()`, the mirror pass consumed `m_updateAllKeys` / `m_doCull`, re-culled bushes/trees/props against the tiny water reflection frustum, double-advanced tree sway/topple/push-aside timers, and drew decals into the reflection target.
  2. **Vertex buffer overflow and corrupted `bufferNdx` (`W3DTreeBuffer.h`, `W3DTreeBuffer::loadTreesInVertexAndIndexBuffers`)**: `MAX_BUFFERS` remained at `1` (30,000 vertices / 60,000 indices), overflowing on dense maps with extended camera heights and draw distances, and `m_trees[curTree].bufferNdx` / `firstIndex` were written before capacity checks caused a `break`.

### Fix W3DModelDraw recoil list crash in China mission 7 (#379)
- **Problem**: In China mission 7, the game crashed during weapon firing due to an out-of-bounds access / empty recoil vector.
- **Root cause (`W3DModelDraw.cpp`)**:
  - `specificBarrelToUse > wbvec.size()` allowed indexing at `wbvec.size()`, which is an off-by-one out-of-bounds error.
  - The recoil list `m_weaponRecoilInfoVec[wslot]` is sized when the model state is set. If that occurs before the shared weapon barrel info of the state is validated (only built during a logic update), the recoil list remains empty when weapon fire effects or client recoil updates trigger, causing an out-of-bounds access or assertion failure.
- **Fix**:
  - Fixed off-by-one boundary check: `specificBarrelToUse >= (Int)wbvec.size()`.
  - Synchronized recoil lists across all weapon slots to their validated barrel count in both `handleWeaponFireFX()` and `handleClientRecoil()`, preserving existing recoil states while preventing out-of-bounds access and assertion failures.
  - Patch originally reported and provided by [@Moortu](https://github.com/Moortu).

### Fix OpenAL audio stream hissing voice sound (#380)
- **Problem**: In campaign maps, voice lines could leave behind a continuous hissing or looping sound artifact.
- **Root cause (`OpenALAudioStream.cpp`)**: When an OpenAL source transitions to `AL_STOPPED`, it has completed playback of all queued buffers, and OpenAL flags them as processed. Calling `play()` on a stopped source rewinds it and replays the old buffers again. Consequently, the final chunk of speech lines looped indefinitely and the stream was never released.
- **Fix**:
  - In `OpenALAudioStream::update()`, explicitly detect `sourceState == AL_STOPPED && num_queued > 0`, unqueue and drop stale played buffers while preserving any freshly queued buffers added immediately prior to `update()`.
  - Restricted the subsequent restart check to `AL_INITIAL` and `AL_PAUSED`.
  - Patch provided by [@Moortu](https://github.com/Moortu) with subsequent frame preservation hardening.

### Fix menu freeze when transition target window is missing (#381)
- **Problem**: In Generals base game (and in Zero Hour under issue #381 when `PatchWindow.big` was disabled), clicking "Single Player" ("Um Jogador") entered the submenu, but all buttons—including "Back" ("Voltar")—were unresponsive to mouse clicks. The game could not be navigated or exited normally, forcing players to terminate it via Cmd+Q or Alt+F4.
- **Root cause (`GameWindowTransitionsStyles.cpp`, `GameWindowTransitions.cpp`)**:
  - When entering a submenu, `MainMenu.cpp` sets `dontAllowTransitions = TRUE`, and all submenu buttons begin with `if (dontAllowTransitions) break;`.
  - Every frame in `MainMenuUpdate()`, `dontAllowTransitions` is cleared only when `TheTransitionHandler->isFinished()` returns `TRUE`.
  - When a transition group references a window name that does not exist in the active layout (e.g. `MainMenu.wnd:ButtonCustomMission` in Zero Hour when `PatchWindow.big` is renamed to `.bak`, or `MainMenu.wnd:ButtonTRAINING` in Generals base when layout variations occur), `TheWindowManager->winGetWindowFromId()` returns `nullptr`.
  - In `GameWindowTransitionsStyles.cpp`, all transition styles checked `if (!m_isForward || !m_win) break;` at `END` (forward) and `if (m_isForward || !m_win) break;` at `START` (reverse). When `m_win` was `nullptr`, execution bailed out early without setting `m_isFinished = TRUE`.
  - Consequently, `TheTransitionHandler->isFinished()` permanently evaluated to `FALSE`, preventing `dontAllowTransitions` from ever clearing and freezing the UI state machine indefinitely.
- **Fix**:
  - In `Core/GameEngine/Source/GameClient/GUI/GameWindowTransitionsStyles.cpp`, updated all transition style implementations (`FlashTransition`, `ButtonFlashTransition`, `FadeTransition`, `ScaleUpTransition`, `ScoreScaleUpTransition`, `MainMenuScaleUpTransition`, `MainMenuMediumScaleUpTransition`, `MainMenuSmallScaleDownTransition`, `TextTypeTransition`, `CountUpTransition`, `FullFadeTransition`, `TextOnFrameTransition`) to mark `m_isFinished = TRUE` at completion (`START` frame in reverse, `END` frame in forward) even when `m_win` is `nullptr`.
  - Guarded all `m_win` operations (such as `winHide()`, `winGetSize()`, `winGetScreenPosition()`, and `winGetInstanceData()`) against `nullptr` dereferencing.
  - Hardened missing-window handling across all transition classes: guarded `update()`, `reverse()`, `skip()`, and `draw()` so missing-window instances remain finished (`m_isFinished = TRUE`) and inert during group reversals, zeroed geometry increments on fallbacks, and prevented audio events or display string dereferences when target windows are missing.
  - In `Core/GameEngine/Source/GameClient/GUI/GameWindowTransitions.cpp`, added a warning log in `TransitionWindow::init()` when a target window cannot be resolved (`[WARNING] TransitionWindow::init: Window '%s' not found for transition style %d`).

### Fix Microwave Tank heat distortion effect glitching and displaying UI (#384)
- **Problem**: In Zero Hour on Linux and macOS, the Microwave Tank's heat distortion / microwave wave effect glitched continuously, rendering pieces of the user interface (command bar, radar, portraits) across the microwave cone instead of the intended heat shimmer refraction.
- **Root cause (`W3DSmudge.cpp`)**:
  - `W3DSmudgeManager::render()` rendered the refractive heat smudges by copying the background image using `background->Copy(..., backBuffer)`, where `backBuffer` was retrieved via `DX8Wrapper::_Get_DX8_Back_Buffer()`.
  - In retail DirectX 8, 3D scenes were rendered directly to the backbuffer before the UI was drawn. However, in GeneralsX, post-processing (`TheW3DPostProcess->beginScene()`) redirects 3D scene rendering to an offscreen render target (`m_sceneSurface`), only blitting the composited result to the backbuffer after `drawViews()` finishes and before `TheInGameUI->DRAW()`.
  - Furthermore, in Vulkan/DXVK, `GetBackBuffer()` references the swapchain backbuffer, which during 3D world rendering retains the previous frame's rendered content (including the fully drawn UI/HUD).
  - Consequently, `W3DSmudgeManager` copied the previous frame's backbuffer containing the user interface, causing the microwave distortion quads to sample and distort buttons, radar, and fonts instead of the active 3D world.
- **Fix**:
  - In `W3DSmudgeManager::ReAcquireResources()` and `W3DSmudgeManager::render()`, dynamically obtain the active render target via `pDev->GetRenderTarget(&renderTargetD3D)` (falling back to `_Get_DX8_Back_Buffer()` if unavailable).
  - Automatically re-create `m_backgroundTexture` if its dimensions or format differ from the active render target (e.g. resolution change or offscreen surface formats).
  - Copy the background from the active render target rather than the swapchain backbuffer, ensuring that refractive smudges distort the active 3D scene prior to post-processing and UI rendering.
  - Explicitly reset texture stage 0 to `nullptr` upon completing smudge drawing to prevent texture-as-render-target hazards on subsequent render passes.

### Fix asset root resolution for launcher-managed workspaces (GenHub) and portable setups (#416)
- **Problem**:
  - When running GeneralsX from custom launchers such as [GenHub](https://github.com/community-outpost/GenHub) or portable workspaces on Windows, the engine mounted the vanilla retail installation from the Windows registry instead of scanning the workspace directory where `GeneralsXZH.exe` was executed. Consequently, game mods and content symlinked or materialized in the workspace were completely ignored.
  - Without a trailing backslash in `Options.ini` (`AssetPath = .\`) or environment variables (`CNC_GENERALS_ZH_PATH`), asset scanning silently failed with `[ASSET_ROOT] Env path '...' did not provide BIG files`, falling through to the registry.
- **Root cause**:
  - In `Core/GameEngineDevice/Source/Win32Device/Common/Win32LocalFileSystem.cpp`, `getFileListInDirectory()` concatenated `directory` and `searchName` (and subdirectory components) without ensuring a directory separator. If `currentDirectory` had no trailing separator (e.g. `C:\Games\ZeroHour`), `FindFirstFile()` queried `C:\Games\ZeroHour*.big` in the parent directory rather than `*.big` within the folder, and appended filenames as `C:\Games\ZeroHourINIZH.big`, causing file lookups to fail.
  - In `Core/GameEngine/Source/Common/System/BIGFileSystem.cpp`, `loadPrimaryGameAssets()` checked the Windows registry (`GetStringFromRegistry("", "InstallPath", defaultPath)`) before checking the executable directory (`exeDirectory`). Since retail or digital registry entries almost always exist on Windows, the engine always prioritized the registry over the folder from which the executable was launched.
  - In `loadBaseGeneralsAssetsForZH()`, the base Generals registry was checked before checking nested `ZH_Generals` in the active Zero Hour root.
- **Fix**:
  - **`Win32LocalFileSystem.cpp`**: Ensured trailing directory separators between `originalDirectory` and `currentDirectory`, and ensured `directory` ends with a separator before appending `searchName` or `findData.cFileName`. Maintained cumulative relative separators during recursive subdirectory traversal.
  - **`BIGFileSystem.cpp`**:
    - Added `hasPrimaryGameArchive()` helper to check whether a directory contains core game archives, strictly requiring `INIZH.big` for Zero Hour and `INI.big` for base Generals (and similarly `INI.big` in `hasBaseGeneralsArchive`) to prevent partial directories with only Maps or Speech from prematurely overriding complete registry installs.
    - In `loadPrimaryGameAssets()`, added check for complete installations in `exeDirectory` (`hasPrimaryGameArchive(exeDirectory)`) with tag `default-exedir-complete` *before* checking the Windows registry, allowing launcher-managed workspaces and portable installs to work out of the box.
    - Added command-line flag `-assetPath <dir>` (highest priority).
    - In `tryResolveFromIni()`, sanitized paths and added fallback resolution relative to `exeDirectory` when relative paths are specified in `Options.ini`.
    - In `loadBaseGeneralsAssetsForZH()`, added `-generalsAssetPath <dir>` command-line flag and prioritized local `ZH_Generals` in the active Zero Hour asset root or executable directory over the base Generals registry.
  - **`CommandLine.cpp` & `GlobalData.h`**:
    - Added `m_assetPath` (Generals & Zero Hour) and `m_generalsAssetPath` (Zero Hour) to `GlobalData`.
    - Added `parseAssetPath()` and `parseGeneralsAssetPath()` to `paramsForStartup[]`.
  - **Documentation**:
    - Updated `README.md` with runtime asset paths and launcher workspace instructions.
    - Updated Wiki (`How-to-Install-GeneralsX.md`) with a dedicated guide on running from launcher-managed workspaces, detailing resolution order, automatic detection, command-line arguments, and `Options.ini` overrides.
