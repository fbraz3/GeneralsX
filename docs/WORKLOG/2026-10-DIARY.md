## 2026-10-02: Fix Replay Test Crash 0xC0000139 (OpenSSL QUIC TLS Entrypoint Mismatch in Windows SDL3 Bundle)

### Context & Root Cause
1. **Windows SDL3 Replay Tests Loader Crash (`0xC0000139`)**:
   - In CI run 36952546727, all build jobs passed across macOS, Linux, and Windows, but `Replay Tests (windows SDL3 x64)` failed with exit code `-1073741511` (`0xFFFFFFFFC0000139`, `STATUS_ENTRYPOINT_NOT_FOUND`) with zero console output.
   - Comprehensive PE import/export table analysis of the packaged bundle (`windows-bundle-generalsxzh-windows64-deploy`) identified 3 missing entrypoints:
     - `libcurl-4.dll` imported `SSL_set_quic_tls_early_data_enabled` from `libssl-3-x64.dll`.
     - `libngtcp2_crypto_ossl-0.dll` imported `SSL_set_quic_tls_cbs` from `libssl-3-x64.dll`.
     - `libngtcp2_crypto_ossl-0.dll` imported `SSL_set_quic_tls_transport_params` from `libssl-3-x64.dll`.
   - The root cause was DLL collision between vcpkg and MinGW MSYS2:
     - `deploy-windows-zh.ps1` and `deploy-windows-generals.ps1` copied vcpkg DLLs first, placing vcpkg's MSVC OpenSSL 3.x build of `libssl-3-x64.dll` into `$bundleDir`.
     - MinGW MSYS2 compiles `libcurl-4.dll` and `libngtcp2_crypto_ossl-0.dll` against MSYS2's OpenSSL 3.x build with QUIC extensions.
     - When the transitive dependency resolver scanned dependencies, `libssl-3-x64.dll` was already present in the bundle directory, so it skipped resolving it from `$mingwBin`.
     - At startup, the Windows dynamic loader attempted to bind `libcurl-4.dll` to vcpkg's `libssl-3-x64.dll`, failed on the missing QUIC TLS functions, and terminated `GeneralsXZH.exe` with `0xC0000139`.

### Changes Applied
1. **Prioritize MSYS2 OpenSSL Runtime in Deploy Scripts (`deploy-windows-zh.ps1`, `deploy-windows-generals.ps1`)**:
   - Added `"libssl-3-x64.dll"` and `"libcrypto-3-x64.dll"` to `$coreMinGwDlls` so they are copied with `-Force` directly from `$mingwBin`, replacing vcpkg's OpenSSL binaries.
   - Verified with PE analysis that MSYS2's `libssl-3-x64.dll` exports all 603 symbols (including all QUIC TLS symbols), resolving all entrypoints to 0 missing.
   - Added removal of redundant vcpkg `libcurl.dll` when MinGW's `libcurl-4.dll` is present to eliminate runtime loader ambiguity.
   - Added a sweep step to remove stray vcpkg debug runtime DLLs (`libcurl-d.dll`, `libprotobufd.dll`, `libprotocd.dll`, `zlibd1.dll`).
2. **CI Bundle Verification (`build-windows-sdl3.yml`)**:
   - Added `libssl-3-x64.dll` and `libcrypto-3-x64.dll` to `$requiredDlls` in the bundle verification step to guarantee both OpenSSL runtime libraries are validated on every build.

## 2026-10-02: Fix Windows SDL3 Replay CI Completion Detection from Combined Console Output

### Context & Root Cause
1. **Windows SDL3 Replay False-Negative Failure (`missing completed Game Time marker`)**:
   - In CI run 37087012843, following the OpenSSL QUIC entrypoint fix (commit `f147c90c5`), all build jobs passed and `GeneralsXZH.exe` launched and executed cleanly on `Replay Tests (windows SDL3 x64)` without loader crashes (`exit 0`).
   - All 6 test replays ran to 100% completion in headless mode (`07:10/07:10`, `06:38/06:38`, `14:39/14:39`, `08:39/08:39`, `06:07/06:07`, `12:15/12:15`), but the job failed with `missing completed Game Time marker` for all 6 replays.
   - The root cause was that `.github/workflows/replay-tests-windows.yml` searched for completion markers exclusively in `$stdoutOutput`:
     ```powershell
     $completionLines = @($stdoutOutput | Select-String -Pattern '^Elapsed Time: \d{2}:\d{2} Game Time: (\d{2}:\d{2})/\1$')
     ```
   - In MinGW-w64 builds of GeneralsX, console diagnostic logging uses `fprintf(stderr, ...)`, routing all engine and simulation status to standard error (`$stderrOutput`). Consequently, `$stdoutOutput` was 0 bytes, causing the match count to be 0 and falsely flagging completed replays as failures.
   - Additionally, strict line start `^` and end `$` anchors in the regex could be susceptible to trailing carriage return `\r\n` characters on Windows runner streams.

### Changes Applied
1. **Evaluate Combined Console Streams (`.github/workflows/replay-tests-windows.yml`)**:
   - Updated `$completionLines` search to evaluate `$output` (which merges `$stderrOutput` and `$stdoutOutput`), providing parity between MSVC x86 and MinGW x64 runtime logging.
   - Relaxed regex anchors to `'Elapsed Time: \d{2}:\d{2} Game Time: (\d{2}:\d{2})/\1'` and trimmed the resulting completion line string (`$completionLines[-1].Line.Trim()`).
   - Refined error diagnostic filtering in the failure path to exclude normal termination substrings (`returned with code`, `Exiting`), retaining true errors (`Error|CRC|MISMATCH|FATAL|Cannot open replay`).

## 2026-10-03: Optimize Windows SDL3 CI Build Time via ccache PCH Support, Path Normalization, and FetchContent De-caching

### Context & Root Cause
1. **Windows SDL3 64-bit CI Pipeline Duration Bottleneck**:
   - In CI run 37137138473, while Linux and macOS build jobs finished in ~10–15 minutes, the Windows SDL3 job (`generalsxzh@windows64-deploy`) took ~46–50 minutes total (compilation alone took 33m 31s).
   - Detailed step telemetry analysis identified three distinct compounding root causes:
     1. **`Cache CMake FetchContent` Anti-Pattern**: Restoring `build/windows64-deploy/_deps` took 5m 44s to decompress ~700 MB of >40,000 files on Windows NTFS. Worse, timestamp and mtime shifts between the cached build tree and the fresh repository checkout caused CMake and Ninja to recompile `_deps` (such as SDL3 and DXVK) anyway. Fresh Git cloning of the FetchContent dependencies on Azure runners takes only ~25 seconds, making caching 15x slower than cloning fresh.
     2. **ccache Hit Rate Collapse on Precompiled Headers (`pch_defines`)**: In the build log, ccache reported 2,444 uncacheable calls and 1,124 misses out of 1,600 compiler invocations during the build (71% miss rate). GeneralsX extensively uses precompiled headers (`target_precompile_headers` on `z_gameengine`, `z_ww3d2`, `z_gameenginedevice`, `core_wwlib`, etc.). Without `pch_defines` enabled in `CCACHE_SLOPPINESS`, GCC treats all compilations using precompiled headers as uncacheable or misses.
     3. **`CCACHE_BASEDIR` Path Separator Mismatch**: In `build-windows-sdl3.yml`, `${{ github.workspace }}` expanded with Windows backslashes (`D:\a\GeneralsX\GeneralsX`), whereas MinGW GCC and CMake invoke compilers using forward slashes (`D:/a/GeneralsX/GeneralsX`). Because ccache performs exact prefix matching, this slash mismatch prevented basedir relative rewriting, causing ccache to hash absolute file paths.
     4. **CMake Environment Variable Overwrite**: `cmake/ccache.cmake` unconditionally ran `set(ENV{CCACHE_SLOPPINESS} "time_macros,include_file_mtime,locale")` during configure, overwriting external environment settings and excluding `pch_defines`.
     5. **Ninja Parallelism Throttling**: `build-windows-zh.ps1` and `build-windows-generals.ps1` hardcoded `-j4`, artificially throttling Ninja concurrency during I/O waits and ccache hashing.

### Changes Applied
1. **De-cache FetchContent (`.github/workflows/build-windows-sdl3.yml`)**:
   - Removed the `Cache CMake FetchContent` step, immediately eliminating ~6 minutes of cache archive extraction overhead and avoiding stale build-tree timestamp conflicts.
2. **ccache Precompiled Header & Sloppiness Support (`cmake/ccache.cmake`, `.github/workflows/build-windows-sdl3.yml`)**:
   - Added `pch_defines` and `include_file_ctime` to `CCACHE_SLOPPINESS`: `pch_defines,time_macros,include_file_mtime,include_file_ctime,locale`.
   - Updated `cmake/ccache.cmake` to avoid overwriting `ENV{CCACHE_SLOPPINESS}` if already defined in the environment.
   - Normalized `CCACHE_BASEDIR` and `CCACHE_DIR` with forward slashes (`.Replace('\', '/')`).
   - Bumped the ccache cache key prefix to `ccache-windows-sdl3-v2-` to ensure a clean cache populated with normalized relative paths.
3. **Uncap Compilation Parallelism & Verbose Telemetry (`scripts/build/windows/build-windows-zh.ps1`, `build-windows-generals.ps1`)**:
   - Replaced hardcoded `-j4` with dynamic parallelism that respects `$env:CMAKE_BUILD_PARALLEL_LEVEL` if defined, otherwise allowing Ninja to use its optimal native thread pool (`cores + 2`).
   - Updated `ccache -s` to `ccache -s -v` for detailed cache diagnostics in CI output.
