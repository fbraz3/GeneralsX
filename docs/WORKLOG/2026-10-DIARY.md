### Fix volumetric shadow heap overflow that crashed the memory pool, and the ASan build
- **Crash**: SIGSEGV in `MemoryPoolSingleBlock::setNextFreeBlock` while playing the ShockWave Nuke General challenge on Linux. The free list of `dmaPool_512` contained 16-bit triangle index data, so some earlier code wrote past its block into the next block's header.
- **Root cause (`W3DVolumetricShadow.cpp`, Generals + GeneralsMD)**: `allocateSilhouette()` sized the silhouette edge list as `numVertices * 5`, but `buildSilhouette()` adds up to 3 edges (6 indices) per polygon, for example for polygons without neighbors (`addNeighborlessEdges()`). Meshes with many open edges overflowed the silhouette. The shadow volume `Geometry` is sized from `m_maxSilhouetteEntries`, so `constructVolume()` also wrote one triangle past the volume index buffer.
- **Fix**: New `silhouetteEntries()` returns `max(numVertices * 5, numPolygons * 6)`, used by `allocateSilhouette()`. `SetGeometry()` now reallocates when the new geometry needs more entries than are allocated (it compared vertex counts with the previous geometry before), and drops the shadow volumes of that mesh so `updateMeshVolume()` allocates them again with the new size.
- **ASan build (`GameMemoryNull.cpp`)**: `sizeof MemoryPoolFactory` without parentheses does not compile with GCC. It is only built with `RTS_GAMEMEMORY_ENABLE=OFF`, for example with `RTS_BUILD_OPTION_ASAN=ON`.
- **`Is_Valid_Float` / `Is_Valid_Double` (`wwmath.h`)**: read the value through an `unsigned long` pointer, which is 8 bytes on 64-bit Linux. ASan reported a stack-buffer-overflow for `Is_Valid_Float`. In `Is_Valid_Double`, the `+ 1` on that pointer moved the read past the double, so it read unrelated memory. Both now `memcpy` the bits into `uint32_t` / `uint64_t`.
- **Validation**: Linux `linux64-deploy` build of `z_generals` with `RTS_BUILD_OPTION_ASAN=ON` and `-fsanitize-recover=address`. Before the fix, ASan reported heap-buffer-overflows in `addSilhouetteIndices`, `constructVolume`, `Geometry::SetPolygonIndex` and `RenderDynamicMeshVolume`. After the fix, the ShockWave Nuke General challenge played to the end on Arch.

### Fix macOS fullscreen black screen loop caused by DXVK swapchain reset failure
- **Diagnosed Black Screen in Fullscreen Mode on macOS**:
  - Investigated execution logs (`logs/run_zh_macos.log`) and verified using downloaded macOS release artifact (`GeneralsXZH.app`).
  - While windowed mode (`-win`) rendered properly, fullscreen mode on macOS consistently resulted in a solid black screen while audio played and mouse clicks registered.
- **Identified Root Causes**:
  1. **Asynchronous Cocoa Fullscreen Window Resizing**:
     - On macOS, SDL3 creates the window before the Cocoa asynchronous fullscreen animation finishes, initializing D3D8 swapchain backbuffer dimensions to an intermediate size (e.g., `2048x1536`).
     - On the next frame, Cocoa completes the transition and reports the native Retina physical resolution (`2880x1800`), causing `Pillarbox_Process_Resize()` to detect a dimension mismatch and trigger `DX8Wrapper::Reset_Device()`.
  2. **DXVK Strict Losable Resource Accounting in D3D8 Emulation**:
     - DXVK emulates D3D8 on top of its D3D9 layer. By default, `d3d9.countLosableResources = True`.
     - When `Reset_Device()` called `m_pDev->Reset()`, DXVK rejected the swapchain recreation because alive `D3DPOOL_DEFAULT` subresources remained referenced:
